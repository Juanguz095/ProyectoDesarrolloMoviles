# P0.1 — Inventario y comprobación del prototipo

Fecha: 17 de octubre de 2026. Revisión: checkout de trabajo sin commits; rama `work`. Entorno: Debian 13, Python 3.12.14, Node 24.19.0. Todos los datos y credenciales de las pruebas son ficticios, generados temporalmente y eliminados al terminar.

## Ejecución y resultados

| Comando desde la raíz | Resultado |
| --- | --- |
| `python3 -m unittest discover -s backend/api/tests -v` — primera ejecución | Salida 1: 15 métodos ejecutados; 3 fallos de aserción y 4 errores en subcasos de tipos JSON. |
| `.venv/bin/python scripts/check_contract.py` — primera ejecución | Salida 1: YAML inválido en `EnrollmentRequest`. |
| `python3 -m unittest discover -s backend/api/tests -v` — tras correcciones | Salida 0: 16 pruebas aprobadas, ninguna omitida. |
| `node --test backend/api/tests/revocation.test.cjs` | Salida 0: 2 pruebas aprobadas, ninguna omitida. |
| `.venv/bin/python scripts/check_contract.py` — tras corrección | Salida 0: OpenAPI 3.1 válido, versión 0.1.0, 9 rutas. |

Los tests levantan un servidor HTTP real en loopback y puerto efímero con una BD temporal distinta por prueba. Ejercitan login/roles, consentimiento, inscripción de un uso y vencida, inscripción concurrente, recepción, duplicados, errores, aislamiento, filtros, CSV, auditoría y revocación local/remota. La retención comprobada es la del prototipo, disparada al consultar. La persistencia se comprueba reabriendo la base e inicializando de nuevo el esquema.

Las dos comprobaciones JavaScript ejecutan el manejador real de la página en Node con DOM/red simulados: verifican que el token local y el envío se deshabilitan antes de completar la solicitud de revocación, tanto con éxito como con fallo de red.

## Defectos reproducidos y corregidos

1. `category`/`direction` como lista y metadatos enum como objeto provocaban `TypeError` y cierre de conexión. Ahora devuelven `400` controlado.
2. Un evento con `acceptedAt` distinto del consentimiento inscrito se aceptaba. Ahora devuelve `409` sin persistirlo.
3. Reutilizar un ID con distinto contenido se consideraba un duplicado válido. Ahora devuelve `409`; el mismo contenido sigue siendo idempotente.
4. Un usuario desconocido devolvía error de configuración `503`. Ahora recibe `401` como una contraseña incorrecta.
5. La indentación de `EnrollmentRequest` impedía leer el contrato; se corrigió y validó con un validador OpenAPI.
6. Los errores usaban `application/json` aunque el contrato declaraba `application/problem+json`; se alineó el servidor.
7. La web esperaba la respuesta de revocación antes de detener el envío. Ahora detiene localmente primero.
8. Se añadió transacción explícita de escritura al consumir el código de inscripción; dos peticiones simultáneas producen una sola inscripción.

## Límites que pasan al producto definitivo

- No se ejecutó un navegador real ni un dispositivo Android. Servir el HTML y probar un manejador aislado no valida toda la UI.
- La credencial web vive en memoria; no hay Room, WorkManager, Keystore, notificación Android ni recuperación durable de revocación offline.
- JWT artesanal, cuentas por entorno, sin refresh ni límites de login: referencia local únicamente; reemplazar en P3.1.
- Idempotencia actual por ID global; P2.3/P3.3 deben usar `(deviceId, eventId)`.
- Retención por timestamp del evento, solo con tráfico; no satisface CA-11 del producto definitivo.
- Auditoría no conserva filtros/resultado/correlación; CSV sin filtros y sin paginación real. Completar P3.4/P3.5.
- Algunas solicitudes de login/inscripción no rechazan campos extra; completar contrato estricto en el backend definitivo.
- El prototipo responde dentro de contextos de transacción; el backend definitivo debe confirmar commit antes de anunciar éxito.
- No se validó HTTPS, despliegue, firma de APKs ni pruebas de aceptación Android.

Conclusión: **P0.1 verificada como inventario y diagnóstico del prototipo**, sin declarar completados los criterios del producto final. Siguiente tarea: P0.2, herramientas y compilación mínima Android/PostgreSQL.
