## Fallos encontrados y corregidos en la preparación

1. **Robolectric en un home de solo lectura:** las cuatro pruebas del agente fallaban en `.robolectric-download-lock`. `scripts/gradle.py` ahora configura `user.home`, proxy y CA también para las JVM hijas mediante `JAVA_TOOL_OPTIONS`. Se repitieron las siete pruebas; todas aprobaron. No se cambiaron sus aserciones ni versiones.
2. **CA explícita reemplazada por la ambiental:** la comprobación TLS llegó a fallar en Requests aunque curl aceptaba la CA. Se pasó la CA seleccionada en cada solicitud de `check_live_contract.py`, conservando la verificación y el proxy. La repetición completa TLS/contrato/cliente aprobó, incluido el rechazo sin confianza.
3. **Aislamiento del test PostgreSQL:** `check_database.py` ahora limpia todas las variables `AUDITLAB_*` heredadas antes de configurar su instancia nueva, para no heredar una cuenta de mantenimiento o un puerto TLS ajenos. Sus temporales se crean bajo `.tooling/database-check-tmp/`. Los 53 casos se repitieron satisfactoriamente, también con una URL de mantenimiento deliberadamente inaccesible y rutas TLS inexistentes heredadas como centinelas. Esa ejecución aprobó sin utilizar esos valores ni tocar el fixture API persistente.
4. **Rutas y control del fixture:** el chequeo TLS usa por defecto `.tooling/tls-check`. El control del proceso API valida PID, instante de creación y clase/ruta sin depender de enlaces `/proc/PID/cwd` no accesibles en esta nube. Se comprobó detener/arrancar sin pérdida de datos.

## API30: Android arrancó, UI no validada

Se descargó la imagen oficial `system-images;android-30;default;x86_64`. AVDs separados de los académicos en `.tooling/integration-avds/`. Android Emulator 37.2.12, 2048 MiB de RAM, dos vCPU, pantalla 720×1280/densidad320, SwiftShader y Vulkan desactivado, `-accel off`, sin snapshots. No hay `/dev/kvm`.

La preparación encontró falta de disco para la partición de datos: el emulador ajusta el tamaño a 6 GiB y pide aproximadamente 7,2 GiB libres. Se conservaron esos rechazos. Se retiró mediante SDK Manager únicamente la imagen de sistema descargable API36 y seis instaladores ya extraídos, guardando sus hashes. Se conservaron herramientas, plataformas de compilación, AVDs, datos y evidencias. La imagen API36 puede reinstalarse antes de volver a usar sus AVDs.

Después de resolver el espacio:

1. El primer API30 completó `sys.boot_completed=1` y se instaló el APK del agente mediante `adb install -r -t`. `am start -W` abrió su actividad.
2. Solo después del primer arranque se inició el segundo API30 de 2 GiB. También completó el arranque; su espera registró 262 s. No se instaló ni ejecutó el centro en ese AVD.
3. La captura real del agente mostró **«System UI isn't responding»** sobre la pantalla de consentimiento. El árbol UI solo contenía los botones del diálogo del sistema. No se otorgó consentimiento, no se inscribió el agente y no se ejecutó el recorrido entre las apps.
4. Se conservaron capturas y diagnósticos y se detuvieron los procesos propios. El reinicio aislado inicial fue rechazado por un bloqueo residual cuyo PID ya estaba zombie. Tras verificar propiedad y ausencia de procesos activos, se retiró solo esa metadata de bloqueo; no se borró userdata.
5. Se repitió el arranque usando solo el primer AVD y sus datos ya preparados. Volvió a completar el boot, pero la comprobación UI volvió a detectar **el ANR de System UI**. El intento se marcó fallido. No se cerraron los diálogos ni se relajaron las comprobaciones para obtener un aprobado.
