# P2.3 — Migraciones PostgreSQL, bootstrap e infraestructura Ktor

Fecha: 17 de octubre de 2026. Revisión: checkout `work` sin commits. Entorno: Linux amd64, JDK 21.0.12.1, Gradle 8.11.1, PostgreSQL 17.6 en contenedor temporal con contraseña generada. No se usó una BD existente del usuario.

## Entregables

- Migración SQL versionada para ocho tablas, relaciones, checks e índices; historial y validación Flyway, sin `clean`.
- Clave de evento por dispositivo/ID, consentimiento vinculado al dispositivo y referencias diferidas para inscripción consistente; refresh padre/hijo dentro de la misma sesión.
- Roles separados de migración/runtime/mantenimiento con grants explícitos. Runtime sin modificación de usuarios, DDL, historial Flyway o actualización/borrado de eventos/auditoría.
- Bootstrap de usuarios por CLI con Argon2id aleatorio, sin contraseña en código ni reseteo implícito de cuentas existentes; creación y auditoría transaccionales.
- Pool Hikari, `/health` y `/ready` diferenciados, CLI `migrate`, `bootstrap-user`, `grant-runtime`, `grant-maintenance` y guías de operación.
- [Modelo e instrucciones](../base-datos.md), [ADR 0002](../decisiones/0002-contratos-y-persistencia.md), tests JVM y fixture PostgreSQL reproducible.

### Cobertura de restricciones y privilegios

Se comprobaron nombre de cuenta único sin distinguir mayúsculas, hash verificable y no rotado por bootstrap repetido, roles permitidos, ID de evento repetido en mismo/otro dispositivo, FK de consentimiento ajeno, tipos/metadatos/enums inválidos, relaciones de inscripción incompletas al forzar commit, hijo refresh de otra sesión, hijo duplicado, append de auditoría por runtime y rechazo de UPDATE/DELETE/DDL/historial Flyway. La cuenta de mantenimiento puede eliminar y no reescribir auditoría. El pool conecta con la cuenta runtime limitada.

No se aceptó un test sin aserción negativa ni un resultado antiguo como prueba de esta BD. Los casos esperaban SQLSTATE de restricción/permisos, no cualquier excepción SQL.

## Fallos encontrados durante el desarrollo

1. El verificador inicial usaba los valores Argon2 predeterminados de la biblioteca (memoria distinta de la elegida para hashing): un test rechazó la contraseña correcta. Se cambió a `Argon2Function.getInstanceFromHash`; verificaciones positiva/negativa y bootstrap quedaron satisfactorias.
2. Una edición de enum YAML alteró el valor de una acción de auditoría, aunque seguía siendo YAML válido. El fixture positivo falló; se corrigió la indentación y los 49 tests de contrato volvieron a aprobarse.
3. El harness de CLI solo devolvía stdout y no reconocía el mensaje esperado por stderr al faltar contraseña. Se corrigió a salida combinada saneada, conservando la comprobación de exit 2 y de que el comando falla sin credenciales.

## Conclusión y límites

**P2.3 verificada y fase 2 cerrada** junto con P2.1/P2.2. El modelo y sus herramientas funcionan sobre PostgreSQL; el backend HTTP de negocio sigue pendiente de P3.1–P3.5. Tener columnas de sesión/refresh no implementa JWT ni revocación HTTP. Disponer de DELETE no implementa retención programada; tener FK/PK no resuelve por sí solo autorización o idempotencia de contenido.

La disponibilidad comprobada es infraestructura parcial de P3.6; falta verificar el comportamiento completo del servicio final. No se compilaron nuevos APKs ni se realizaron pruebas Android en esta fase, porque su código no cambió. No se hizo commit, push, ejecución GitHub Actions, despliegue o publicación del entorno.
